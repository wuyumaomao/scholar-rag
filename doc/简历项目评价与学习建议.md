# 简历项目评价与学习建议

日期：2026-10-12。依据：`doc/简历参考摘录.md` 与学习版当前源代码。仅评价描述呈现的设计与学习价值，未审计参考项目代码；所有效果数据均未独立验证。以下为建议，不代表用户已批准实施这些功能。

## 对你当前进度的判断

你已经具备 Docling 结构化解析、parent/child 分块、Dense/BM25 双路召回、RRF、可选 Cross-Encoder、Milvus、PostgreSQL、LangChain 生成及 SSE。已有检索对照评测和 HyDE 实验记录。单就检索链路的实现范围与实验记录而言，你不需要通过换向量库或追加框架来追赶这些简历。

当前源码中，`routers/chat.py` 只检索本轮 query，`AnswerGenerator` 输入只有问题与检索证据；会话历史只持久化，没有用于消解指代或生成。无 hits 时拒答，有 hits 时生成，但“有命中”不等于“证据足以支持回答”。引用由提示词约束，尚无独立引用校验。未见模型选择工具、观察结果并继续决策的执行循环。

## 七个项目逐项评价

### 1. 旅行规划多 Agent：适合学习编排，业务约束比 Agent 数量更关键

优势是任务天然包含需求、天气/路线、计划和预算审核，能够演示动态路由、结构化状态、重规划和人工确认。重构经历也比单纯列技术名更有面试价值。

需要追问：预算是否由确定性代码计算？日期和路线是否真实可行？四个 Agent 是否优于一个 Agent 加工具或固定流程？Checkpointer 保存状态，不会自动让模型正确使用记忆；Pydantic 保证字段/类型约束，不保证行程事实正确。“95% 可解析”和“异常退出降低 70%”还需要明确基线。

你可借鉴：结构化任务状态、有限重试、迭代上限、checkpoint 与中断恢复。论文场景可用这些机制处理长任务；人工确认适合需要执行外部动作或确认研究范围的场景，不必给每次检索加审批。学习优先级：中。

### 2. Text-to-SQL 数据分析：业务闭环清楚，适合拓宽第二条技术路线

优势是自然语言到查询、结果到图表可以直接验收；Schema 检索和业务口径检索解决不同错误源，技术选择有业务依据。

需要追问：SQL 能执行并不表示业务含义正确；Router 只能约束路由范围，不能保证没有幻觉。更扎实的实现应包括只读权限、SQL 语法树或语句校验、超时与行数限制，以及 JOIN/聚合/业务口径的结果正确性评测。

你可借鉴：将检索作为工具/任务内部基础能力，使用结构化结果驱动下一步，基于明确错误进行有限纠正。若想拓宽 SQL、数据建模和可视化能力，这适合单独作为第二项目；当前论文系统不必为此增加 Text-to-SQL。学习优先级：当前低，第二项目高。

### 3. nano-cc 科研论文 Agent：与你的方向最接近，最值得借鉴

优势是明确处理多轮指代、证据不足、引用和记忆，并分别评测各组件及端到端流程。它把学习目标从“检索到了什么”扩展到“何时继续检索、何时回答、何时拒答”。

需要追问：七阶段固定编排本身不能证明模型具备自主行动能力；Reflect 若只是再问一次模型，也可能错误地认可不足证据。应展示真实失败样例、二次检索策略和退出条件。端到端 75.7% 比一串高分更值得研究：失败发生在哪一阶段？评测集是否独立于调参？

你可借鉴：多轮 query 改写、工具调用循环、可追踪执行状态、有上限的证据检查/二次检索、组件级与端到端评测。无需依赖 nano-cc 才能学习这些原理。学习优先级：最高。

### 4. 金融投研多 Agent：编排和交互学习价值高，实现负担也大

优势是 Controller/Planner/Worker/Reviewer、依赖调度、MCP、任务事件和暂停恢复形成较完整的 Agent 执行系统。对多来源研究任务，独立检索并行和有依赖的汇总确实可能有价值。

需要追问：LangGraph Send 支持动态分发，但完整 DAG 仍要处理依赖、状态合并、失败传播和重复执行。MCP 统一工具协议，不直接提高推理质量。100 条样例的路由准确率 100% 不能代表整体系统质量。

你可借鉴：先实现研究任务分解与工具观察，再学习 LangGraph、任务状态事件、checkpoint，最后在跨论文比较场景中验证并行检索和汇总。你已有答案 token SSE，新增工具/阶段事件才是进一步的学习点。学习优先级：中高，放在单 Agent 基础之后。

### 5. Hybrid KG-RAG：可探索图谱，需用真正的多跳问题证明收益

优势是向量与图谱检索互补、三元组证据溯源和自动化评估；实体归一化与关系约束比“用了 Neo4j”更能体现理解。

需要追问：父子块解决上下文补全，不等同于多跳推理；图谱也可能引入实体合并错误与关系抽取错误。RAGAS Faithfulness 衡量回答受上下文支持的程度，不直接代表外部事实正确，分数受评估模型和配置影响，不能与不同数据集的指标直接比较。

你可借鉴：回答评测、主张与证据关联。Neo4j 可作为后续实验，用“方法—数据集—指标—结论”的关系回答明确的跨论文问题，再与普通 RAG 对照。你现有 Docling 元素关联并非完整语义知识图谱。学习优先级：回答评测高，图谱中低。

### 6. 学术论文阅读 CLI：范围适中，容易做扎实

优势是路由、论文范围过滤、多轮上下文和持久化边界清楚，适合学习型项目。其明确写“确定性图执行”，有助于解释可控流程与动态决策的取舍。

需要追问：BGE-small-zh 是否适合具体论文语言？按字符估算 token 的误差有多大？只摘要旧用户问题可能遗漏回答中的结论与工具证据；“最近五轮”和“70%”应通过保留关键事实的实验选择。距离阈值还依赖具体相似度定义。

你可借鉴：受限历史窗口、token 预算、带来源的摘要和论文范围约束。基础检索部分与你重叠较多。学习优先级：多轮上下文高，其余低。

### 7. 乌类科普 Hybrid RAG：完整应用思路，记忆设计比技术栈更值得学

优势是邻域扩展、连续区间合并、独立 query 重写和短期/长期记忆结合，解决用户真实追问问题。

需要追问：邻域扩展会增加噪声和 token；长期记忆需要定义来源、写入条件、冲突覆盖和遗忘。用户偏好属于个性化上下文，不应成为论文事实证据。截图没有量化评测，不能判断各机制是否有净收益。

你可借鉴：多轮 query 改写和上下文预算。你已有父子块与相关图像扩展，邻域扩展是另一种策略，应先对照，不必全部叠加。Node.js、MySQL 与现有 FastAPI/PostgreSQL 不构成必须迁移的理由。学习优先级：多轮与预算高，长期记忆中，替换技术栈低。

## 推荐学习顺序

1. **多轮问答**：让“这个方法”“它的缺点”正确关联上一轮实体；分别保存原始问题、检索改写和证据。历史用于理解问题，论文证据用于支持结论。
2. **单 Agent 工具循环**：把现有检索封装成带 schema 的工具，学习模型输出 tool calls、参数校验、工具执行、结果回传、继续决策和终止条件。先用小循环理解原理，再用 LangGraph 对照状态、条件边和持久化的实现。
3. **证据与引用控制**：识别缺少证据的问题；必要时改写检索、限定次数补充证据。区分“引用标识存在”“页码有效”和“证据确实支持主张”，后者需要人工或模型辅助评估。
4. **执行追踪与评测**：记录每轮 query 改写、工具及参数、结果、延迟、token 和退出原因。补充多轮、不可答和引用评测，并比较准确率、耗时与成本；不要求所有机制都带来提升。
5. **跨论文研究与 LangGraph 进阶**：能够单论文稳定问答后，扩展多篇论文范围、分解比较问题、按相同维度汇总，再验证并行、checkpoint 与人工确认的必要性。
6. **按学习兴趣选一项扩展**：MCP 学习工具互操作；Neo4j 学习图谱和多跳查询；Text-to-SQL 学习数据库查询与验证。每项围绕独立问题建立可演示结果。

## 对评论区建议的判断

- Skill、Tool、Hook、Workflow 是不同职责与接口，不是高低级关系。名称应符合实际实现，换名字不会增加自主决策能力。
- Redis 用于缓存或共享状态等问题，Kafka 适合特定异步事件/消息场景，不能自动解决 LLM、解析或 embedding 的计算瓶颈。为了学习可设计受控并发实验，但应说明研究的问题。
- 长期记忆不是所有 Agent 的必选项；单次任务状态和会话上下文有独立价值。关键是能解释边界和失效方式。
- 简历项目数量不必照搬“4 个”。对学习和面试，能够讲清问题、设计取舍、实验和失败分析的项目更有价值。

## 适合你的项目表达方向

可围绕“面向科研论文的可追溯研究助手”持续演进：现有 RAG 作为底座，逐步支持多轮追问、按需工具调用、证据不足处理和跨论文比较。已验证的 Dense/Hybrid/rerank 对照、HyDE 未提升及 fallback 分析，都是可用于面试的真实实验材料。尚未实现的 Agent 功能不应提前写成已完成成果。
